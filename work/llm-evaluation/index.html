Testing LLMs and Databricks platforms for regulated use

Two products I built end to end to qualify a customer’s LLM deployment or Databricks platform for regulated (GxP) use: tests scored on the customer’s thresholds, versioned platform checks and a signed report.

Scope

Two products, built end to end: an LLM test engine with 19 tests scored against the customer’s own thresholds, and a Databricks test engine running 59 versioned definitions on Azure and AWS. There are no outcome numbers on this page. The products measure the customer’s systems, and those results are the customer’s.

Life-sciences companies must qualify an AI model or a data platform before they use it in regulated work. Under their quality rules (GxP), that means showing, with evidence, that it was installed as specified (installation qualification, or IQ) and works as intended (operational qualification, or OQ).

I built the two products Purgo’s customers use to run those checks and produce the report they sign for their auditors, both end to end on the company’s web platform.

Three decisions shaped them: the LLM tests avoid judging prose, platform tests are data and not code, and generated tests must compile against the real API before a reviewer sees them.

How the products fit together

A run can take many minutes, since starting a cluster alone can take a quarter of an hour. So each engine is stateless: it answers at once with a job ID, pushes results after every test, and checks before each test whether the user has stopped the run.

LLM tests that avoid judging prose

The LLM validation product is the newer of the two, and I built it end to end: the UI, the API and the test engine. Its 19 tests are code, unlike the platform product’s definitions below, because each one needs datasets, concurrent calls, statistics and sometimes a second model to grade the answers.

Ten operational (OQ) tests run the model on fixed datasets and compare the results with thresholds the customer sets. Judging free text is the hard part, so the tests avoid comparing prose. Determinism and bias tests make the model answer as JSON with fixed keys and closed lists of answers: determinism means the same JSON every time, and fairness means a case’s four demographic variants get the same answer. Where prose can’t be avoided, a separate judge model grades it against a checklist; the judge is never the model under test.

Nine installation (IQ) tests read how an Azure deployment is set up: region, pinned model version, authentication, access, private networking and audit logging. All 26 thresholds are the customer’s, and every check records its threshold next to the measured value.

Platform tests as data, not code

The platform product checks that a customer’s Databricks workspace is set up and behaves as specified: catalog setup, access control and audit logging, cluster behavior, network and security-group settings, lineage and data sharing. Its engine has 59 versioned test definitions, running on Azure, AWS or both. I wrote the engine and every definition.

A test is a definition the engine reads, not code built into the engine. Each definition is a chain of API calls against the customer’s own workspace, with a small function after each call and one at the end that decides the result.

Each step carries a small function instead of a fixed assertion, because real checks wait and branch: start a cluster, poll until it runs, query, check, clean up. Every HTTP status is a result, since many tests are negative. Each function runs in an isolated scope. On AWS the engine signs each request itself, which lets one executor serve both clouds.

The definitions live in their own repository and every run clones the current version, so a fix goes live without a redeploy and the report records the version it ran. That is also how a change is controlled: every result can be traced to the exact version of the tests that produced it.

Generating tests from requirements

A customer’s requirements document becomes tests in the same format as the built-in ones, which then run alongside them.

A generated test is only a proposal, because its code runs against the customer’s workspace. The writing prompt also carries a list of Databricks objects that LLMs tend to invent.

What a run produces

Each product produces a PDF report built for the reviewer who signs it: for each test, the manual procedure, expected and actual values, and every step’s request and response with credentials removed. It keeps the numbers behind every result, so a reviewer can disagree with a threshold without rerunning anything. The report is signed in the app with embedded DocuSign, and every signing asks the signer to log in again, so each signature belongs to the person who made it.

When things go wrong

A run can also go wrong in ways that are not a failed test, and the engines expect the ones below.

Failures the engines expect, and what the report shows
FailureWhat happens
A call can’t be made at allThe step is marked as an error, later steps still run, and the test can’t pass
A test runs too longStopped at its limit and recorded as an error; the run moves on
The user stops the runFinished results are kept; the rest are marked stopped
Settings are missingThe LLM product refuses the run before it starts; checks that need missing credentials report a skip

What this doesn’t show

  • The hallucination cases and the repeated runs in the determinism test are samples. A pass means the model stayed within the customer’s thresholds on those cases, not that it never invents a value.
  • A qualification is a record from the day it ran. A later change to the model or the platform needs a new run.
