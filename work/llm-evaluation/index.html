Testing LLMs and Databricks platforms for regulated use

Two products for regulated (GxP) teams: one runs 19 tests on a customer’s LLM deployment, the other up to 53 on their Databricks platform. Both record evidence an auditor can read.

Purgo AI, · 2025–26, · 4 min read

Updated October 22, 2026

My part. I wrote the Databricks validation service and all 59 of its test definitions, and built the LLM validation product end to end (UI, API and test engine). I also wrote the pipeline that turns requirements into platform tests, the evidence in both products’ PDF reports and the DocuSign signing flow.

Built with. TypeScript, NestJS, Next.js, PostgreSQL, Python, Azure OpenAI, Databricks, AWS, GCP Cloud Run

Companies in regulated (GxP) work, like pharma, can’t just start using a model or a data platform. They have to qualify it first: show, with evidence, that it was installed as specified (installation qualification, or IQ) and that it works as intended (operational qualification, or OQ). Done by hand, that’s repetitive checking. At Purgo I built two separate products that run those checks automatically and record the evidence: one for LLMs and one for Databricks platforms. They test different things, so each has its own engine. A model is non-deterministic and is judged against thresholds on data. A platform is configuration, so its checks are fixed chains of API calls with a clear pass or fail. One engine for both would have made one of them awkward.

Qualifying an LLM

The LLM validation product is the newer of the two, and I built it end to end: the UI, the API and the test engine. It qualifies a customer’s model with 19 built-in tests. Ten operational (OQ) tests run the model, whether it’s on Azure OpenAI or served from Databricks, on fixed datasets and compare the results with thresholds the customer sets. Customers can also upload their own dataset with expected answers and have it scored the same way. Nine installation (IQ) tests check how an Azure deployment is set up: region, authentication, access control, private networking and whether calls are logged for audit.

Seven of the ten operational tests, and what each one catches
TestWhat it catches
HallucinationInventing a value the source doesn’t contain, on 40 cases with missing fields
Extraction accuracyWrong values in extracted fields, scored per field with F1

Latency under concurrencyFailed or slow calls with 20 concurrent workers
Demographic biasDifferent outputs when only the demographics in a case change
TraceabilityA response that can’t be traced back to the model and the request that produced it

Qualifying a Databricks platform

The platform product checks that a customer’s Databricks workspace is set up and behaves as specified. Its engine runs 59 versioned test definitions in 17 suites: 47 run on both clouds and 6 are specific to each, so a run on one workspace has up to 53. They cover catalog setup, access control and audit logging, cluster behavior, network and security-group settings, lineage and data sharing. Each definition is a chain of API calls against the customer’s own workspace on Azure or AWS, plus a small piece of logic that decides pass or fail and records the expected and actual values. I rebuilt the engine and wrote every definition.

Three choices shape it:

  • Test definitions live in their own versioned repository, apart from the engine, and every report records the version it ran. Updating a test doesn’t need a redeploy, and an auditor can see exactly what was tested.
  • Each definition decides pass or fail itself and records the expected and actual values, so a report never says only “failed”. The finished result includes each step’s request and response, with credentials removed, so a reviewer can see what the platform answered.
  • A run reports progress test by test and can be stopped, because a run against a customer’s own workspace can take a while and shouldn’t have to be all or nothing.

Generating tests from requirements

This is part of the platform product. A customer can upload a requirements document (PDF, DOCX or text). An LLM pipeline pulls out the testable statements and writes a platform test definition for each, in the same format as the built-in ones, and the new tests run alongside them. A generated test is a proposal, never trusted as written. The pipeline checks that every definition has all required fields and that its code compiles, and a reviewer approves each one before it runs. If a reviewer rejects one, the pipeline regenerates it with their feedback.

What a run produces

Each product produces its own PDF report. In both, a threshold turns each measurement into a pass or a fail. The report keeps the numbers behind every result, so a reviewer can disagree with a threshold without rerunning anything. A finished report can be signed in the app with embedded DocuSign, and the signed PDF is stored for download.

What this doesn’t show

  • The 40 hallucination cases and the 20 repeated runs in the determinism test are samples. A pass means the model stayed within the customer’s thresholds on those cases, not that it never invents a value.
  • The thresholds are the customer’s, so the same model can pass at one company and fail at another. The report records the numbers so that difference is visible.
  • A qualification is a record from the day it ran. A later change to the model or the platform needs a new run.
  • I don’t report an accuracy for the test engines themselves here.
