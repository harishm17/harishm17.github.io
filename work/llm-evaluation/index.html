Testing LLMs and Databricks platforms for regulated use

Two products that qualify a customer’s LLM deployment or Databricks platform for regulated (GxP) use and record evidence an auditor can sign. Life-sciences customers use them for signed audit reports.

Purgo AI, · 2025–26, · 6 min read

Updated October 28, 2026

My part. I wrote the Databricks validation engine and all 59 of its test definitions, and built the LLM validation product end to end (UI, API and test engine). I also wrote the pipeline that turns requirements into platform tests, both products’ PDF reports and the DocuSign signing flow. The product’s web app, job tracking and scheduler were there before me.

Built with. TypeScript, NestJS, Next.js, PostgreSQL, Python, Azure OpenAI, Databricks, AWS, GCP Cloud Run

Pharma and other regulated (GxP) teams must qualify a model or data platform before using it: show, with evidence, that it was installed as specified (installation qualification, or IQ) and works as intended (operational qualification, or OQ). I built two products that run those checks and record the evidence. Each has its own engine: a model is judged against thresholds on data, while a platform’s checks are fixed chains of API calls with a clear pass or fail.

How the products fit together

The engine is stateless; jobs, settings with encrypted secrets and saved tests live in the product API. A run can take many minutes, since starting a cluster alone can take a quarter of an hour, so the engine answers at once with a job ID, pushes results after every test, and checks before each test whether the user has stopped the run.

Qualifying an LLM

The LLM validation product is the newer of the two, and I built it end to end: the UI, the API and the test engine. It qualifies a customer’s model with 19 built-in tests, whether the model is on Azure OpenAI or served from Databricks. Its tests are code, unlike the platform product’s definitions below, because each one needs datasets, concurrent calls, statistics and sometimes a second model to grade the answers.

Ten operational (OQ) tests run the model on fixed datasets and compare the results with thresholds the customer sets.

Seven of the ten operational tests, and what each one catches
TestWhat it catches
HallucinationInventing a value the source doesn’t contain, on 40 cases with missing fields
Extraction accuracyWrong values in extracted fields, scored per field with F1
ClassificationMisclassified complaints and triage levels, against labeled cases
DeterminismDifferent answers to the same input over 20 repeated runs
Latency under concurrencyFailed or slow calls with 20 concurrent workers
Demographic biasDifferent outputs when only the demographics in a case change
TraceabilityA response that can’t be traced back to the model and the request that produced it

The hard part is judging free text, so the tests avoid comparing prose. Determinism and bias tests make the model answer as JSON with fixed keys and closed lists of answers: determinism means the same JSON every time, and fairness means a case’s four demographic variants get the same answer. Where prose can’t be avoided, a separate judge model grades it against a checklist; the judge is never the model under test.

Nine installation (IQ) tests read how an Azure deployment is set up: region, pinned model version, authentication, access, private networking and audit logging.

All 26 thresholds are the customer’s, and every check records its threshold next to the measured value, so the report shows exactly why a model passed or failed.

Qualifying a Databricks platform

The platform product checks that a customer’s Databricks workspace is set up and behaves as specified: catalog setup, access control and audit logging, cluster behavior, network and security-group settings, lineage and data sharing. Its engine runs 59 versioned test definitions in 17 suites: 47 run on both clouds and 6 are specific to each, so a run on one workspace has up to 53. I rebuilt the engine and wrote every definition.

A test is data, not code in the engine. Each definition is a chain of API calls against the customer’s own workspace, with a small function after each call and one at the end that decides the result.

What one test definition holds
PartWhat it does
StepsAPI calls in order, each with a method, URL, headers and body; values like the workspace URL or a warehouse ID fill in from the run’s variables
After each stepA short function reads the response and adds variables for later steps: an ID to poll, a statement to check
The verdictA function that reads every step’s result and returns pass or fail, with the expected and the actual value
For the auditorThe test’s description and a manual procedure, so a person could repeat it by hand

Steps with a little code, not fixed assertions, because real checks wait and branch: start a cluster, poll until it runs, query, check, clean up. Every HTTP status is a result, since many tests are negative: a user who lacks access must get “access denied”, and that 403 is the pass. Each function runs in an isolated scope, and on AWS the engine signs each request itself, so one executor serves both clouds.

The definitions live in their own repository and every run clones the current version, so a fix goes live without a redeploy and the report records the version it ran.

Generating tests from requirements

A customer’s requirements document becomes tests in the same format as the built-in ones, which then run alongside them.

A generated test is a proposal, never trusted as written, because its code runs against the customer’s workspace. The writing step is grounded in five real tests and a list of Databricks objects models tend to invent, and the code is compiled without running it. A person then edits, drops or regenerates each test, and only valid ones can be saved.

What a run produces

Each product produces a PDF report built for the reviewer who signs it: for each test, the manual procedure, expected and actual values, and every step’s request and response with credentials removed. It keeps the numbers behind every result, so a reviewer can disagree with a threshold without rerunning anything.

A report is signed in the app with embedded DocuSign, and every signing asks the signer to log in again, so each signature belongs to the person who made it.

When things go wrong

Failures the engines expect, and what the report shows
FailureWhat happens
A call returns an error statusIt’s a result: the verdict function decides, and the response is in the evidence
A call can’t be made at allThe step is marked as an error, later steps still run, and the test can’t pass
A test runs too longStopped at its limit and recorded as an error; the run moves on
The user stops the runFinished results are kept; the rest are marked stopped
Settings are missingThe LLM product refuses the run before it starts; checks that need missing credentials report a skip
A generated test is brokenOne automatic retry, then the reviewer sees the errors and can’t save it

What this doesn’t show

  • The hallucination cases and the repeated runs in the determinism test are samples. A pass means the model stayed within the customer’s thresholds on those cases, not that it never invents a value.
  • A qualification is a record from the day it ran. A later change to the model or the platform needs a new run.
