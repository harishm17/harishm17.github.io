ReadableSTEM turns STEM course PDFs into accessible web pages. This page reports how it did on tests I registered before any system ran on them, including the claims I did not make. The newest set tests the design of the product page: the checks against the PDF, the flag policy and the cost of the models.

How the tests were run

I wanted a test I couldn’t tune to, so I wrote down the documents, the metrics and the comparisons before any system ran on them, and hashed the registration. The first set is 15 sections from five OpenStax textbooks (242 pages, 1,369 equations, 509 headings), picked by a seeded rule that excludes every section I used in development. OpenStax publishes these books as web pages with expert-written MathML and alt text, so each section comes with an answer key. I printed each section to a PDF, ran it through the real pipeline and scored the output against the key. Papers from arXiv under open licenses are scored against the authors’ own LaTeX, which is closer to a real course PDF than a printed page: 15 papers (71 pages, 1,826 equations) in the first set and 15 more in each of three later sets.

The comparison is a general chatbot given Purdue’s one-sentence prompt for PDF to accessible HTML, on Claude Opus and on Claude Haiku. Every model call, ReadableSTEM’s included, goes to Claude, so against the Opus chatbot the test is my pipeline against a one-sentence prompt on the same model. The first textbook set also had three open parsers: Docling, MinerU at its basic tier and PyMuPDF4LLM. A few things changed after that registration, and PROOF.md (opens in a new tab) lists each one. At the tag proof-heldout-2026-10, make proof replays that report from the committed model answers with no key and no network.

The fifth fresh set (fresh5) tests the pipeline as it runs today. I signed its registration on November 4, 2026, hashed it, merged it before the first request and ran it once. The primary score is spoken-equal: two equations are equal when ReadableSTEM’s speech rules read them the same, because a screen-reader user hears speech, not markup. I chose that at signing, and on November 3, before any request, I fixed a bug in the scorer that could count one printed equation as two speeches.

Five arms ran: ReadableSTEM at its production settings; the same code with glyph checks, the flag policy and glyph reconcile off, which I call the control; the Opus chatbot and the Haiku chatbot with the Purdue sentence; and an Opus chatbot with a stronger prompt. The units are 12 arXiv papers, 6 OpenStax sections and 8 course LaTeX documents, 3 of them Beamer decks. For the decks I relaxed the gates to 100 characters and 3 equations a slide, from 300 and 5, while the registration was a draft. Three OpenStax chemistry sections (24 pages, 123 equations) are reported separately. Two are licensed CC BY-NC-SA, so I used them privately and publish only totals.

I set the chatbots’ spending caps from a per-page estimate that was too low. The Opus chatbot stopped at its $10 cap after the 26 documents of the first three groups. Before I had seen any ReadableSTEM result I raised the cap to $12.50 so that it answered all 29 documents, and logged the change. The strong-prompt arm stopped at its $9 cap after 17 of 29, so its comparison is on those 17. The run cost $21.98.

What I registered, and how each test came out

The rule for the first textbook set was that a system could be called better only when the 99% interval of the paired difference excluded zero, wider than the usual 95% because there were five comparisons with the chatbot. Later sets used a 97.5% interval for two comparisons and a sign-flip test. Otherwise the wording is “no difference this set can detect”.

The newest set: level on equations, fewer silent errors

Pooled over the 26 documents, ReadableSTEM got 0.840 of equations right end to end (interval 0.791 to 0.876). The Opus chatbot got 0.836 and the Haiku chatbot 0.816. The paired difference from the Opus chatbot is +0.004 (97.5% interval −0.023 to +0.036, p 0.44). The set could detect about 3 points, so the registered wording is no difference this set can detect, and I make no claim in either direction. The same wording holds for the Haiku chatbot (+0.024, p 0.026), the strong-prompt arm on its 17 documents (+0.007) and the control (+0.001).

Silent errors and what the review screen asks

A silent error is a wrong equation that nobody is asked about. A chatbot asks nothing, so all of its wrong equations are silent. ReadableSTEM asks, which is why its number can be lower. For a tool whose job is to tell an instructor what to check, it is the number I care about most.

The paired differences from the Opus and Haiku chatbots are clear, and so is the one from the strong-prompt arm on its 17 documents. The control isolates three design choices. It is ReadableSTEM without glyph checks, the flag policy and glyph reconcile, and it left 6.59. So those three features account for 1.57 fewer silent errors, but the interval only just excludes zero and the sign-flip p is 0.06, so I don’t claim it.

Asking costs the instructor time. ReadableSTEM asked for 2.87 required decisions a page, and its flag recall was 0.461: it asked about 46% of the wrong equations. I registered a recall of 0.60 within 4.0 decisions a page, and silent errors under 4.0. Neither was reached. Replayed on three earlier sets, the flag policy took silent errors from 8.83 to 7.77 per 100 and flag recall from 0.29 to 0.38, and with those features I don’t think 0.60 is reachable. The next equation work has to find a signal the policy doesn’t yet have.

How the equation score came about

The pipeline that produced those numbers changed over five rounds. Each started from the causes I traced in recorded outputs, which costs nothing, before I wrote a fix or spent anything on new runs, and each ended in a test on fresh papers that I registered first. Older sets appear here only for how ReadableSTEM’s own score moved.

Where the misses came from

I took the 25 papers I developed on and gave every equation ReadableSTEM got wrong exactly one cause, the first rule that fit. Five causes carried most of the misses.

The five causes of missed or misplaced equations on the 25 development papers, and the fix for each
CauseWhat happenedThe fix
Short variables in running textA letter set in an italic text font looked like text, so a lone S in a sentence was never an equation.An italic letter between upright words is a variable. A bold letter with an index is a vector.
Where an inline formula starts and endsThe span ran on into whatever sat beside it: the sentence’s parentheses, a unit, a citation or a word.These leave the formula. In a TeX-made PDF the glyphs decide the edges.
Maths in table cellsA cell’s math was the table step’s text, not an equation.A cell that is one formula is an equation of its own, shipped on November 3.
Maths in captionsA caption was kept as one plain string, so a formula in it was never an equation.A caption is cut into text and formulas like a paragraph.
Bold italic lettersA bold vector was read as plain bold.A letter drawn in a bold italic font is written bold italic.

Misreading was not the main cause: among the equations it found, its wrong readings were 6.6% of the answer key. It missed equations because it didn’t see some, or cut them in the wrong place. Three of the causes, on real papers:

Short variables. A letter set in an italic text font looked like text, so a lone S in a sentence was never an equation.

Where a formula stops. The span ran on into whatever sat beside it: the sentence’s parentheses, a unit, a citation.

Captions. A caption was kept as one plain string, so a formula in it was never an equation.

The ideas the evidence ruled out

An obvious next step was a repair loop: render the equation the model wrote, compare the picture with the PDF, and retry on a mismatch. Before building it I checked what it could catch. Of the 282 wrong equations nobody is asked about, 1 had the right symbols in the wrong arrangement, the only kind a render-and-compare check could catch that the text-layer check doesn’t already. The rest had other symbols, which the text-layer check already looks at, or a span cut at an edge, where the render matches the cut and the cut is wrong. One in 282 was far below the bar I had set for building it, so I didn’t build it.

I also had a model read each whole page as a second witness for finding equations. On the development papers it raised the score by 1.7 to 2.5 points but added 0.6 to 1.1 silent errors per 100 equations, against a limit of 0.5, so I fixed the same causes from the text layer instead. In November I built a second version that turns a disagreement between the witness and the crop into a required decision, and tested it on 12 development papers. It changed no reading and found no equation the pipeline had missed, so it hit the stop rule I had written: a gain of 0.0 points against the 2 I needed. It lowered silent errors by 2.1 per 100 by asking about more, at 2.4 cents a page and one more decision a page. It stays off.

The fixes and the tests

The first fixes use the text layer and the position of each glyph, with no change to the prompt, so a recorded model answer replays to the same result. On the development papers the score went from 0.553 to 0.680, which says little, because I tuned on those papers. Each round therefore got a registered test on papers no system had seen:

  • Second fresh set, October 21. The fixes were worth +6.8 points (interval +3.1 to +11.6), from 0.558 to 0.626. Silent errors did not rise: 9.76 per 100 before, 8.42 after. The run cost $13.55 of an $18 cap.
  • Third fresh set, October 23. Column order and a notation convention were worth +0.6 points on the registered score, from 0.614 to 0.620, and +1.8 points when math in table cells counted, from 0.636 to 0.654. The silent-error limit held.
  • Fourth fresh set, October 26. Reading each inline formula with its whole line raised exact equations by 2.6 points (interval +1.7 to +3.6), from 0.586 to 0.613, and silent errors went from 7.9 to 7.3 per 100. The rule I registered for turning it on was met.

Three layers came after the line context: glyph checks, glyph reconcile and the flag policy. I measured them by replaying recorded answers, with no model call. Glyph checks on the fourth set took flag recall from 0.192 to 0.214 and silent errors from 7.25 to 6.38 per 100. The flag policy was fitted on development splits only and then scored with its constants fixed on the second to fourth sets. The newest set is the first held-out run of all three together.

Measured again on the 15 textbook sections on October 21, with these fixes and later changes, it got 0.596 of equations exactly right end to end, against 0.504 in the registered run. That is not a blind result: I had examined those sections since the registered run. The same goes for the November 3 baseline of 0.735 on the 25 development papers, which also counts math in table cells.

Headings and figures

Heading levels and figure descriptions were not registered comparisons, so I report them as descriptive, from the first textbook run (October 14, pipeline version 0.4.0). Heading F1 was 0.961, and among the headings found, the level was right for 1.000 of them (a tool that restores an outline has to get this right). By the judge, 0 of 138 figure descriptions state something the image contradicts, and 0.971 passed. The judge is Claude Opus, which hasn’t been checked against people and is also ReadableSTEM’s main model.

Handwriting goes to review

The handwriting set is 24 pages of real human touchscreen ink, 205 expressions from Google’s MathWriting set, registered before the run. ReadableSTEM got 0.566 of the equations exactly right (interval 0.515 to 0.618), so 43% were wrong. None was silent, because the model called most handwritten blocks medium or low confidence and so 5.7 decisions a page were required, against 1.4 on typed pages. It also dropped four whole display equations of one page without a flag, which the tool now catches by comparing the page’s ink with what it read. The cost was $0.066 a page.

My rule was an advertising bar of 0.50 and zero silent errors, and on the first set both held. On the fresh set the score held (0.589 right on 24 pages, 192 expressions) but the zero did not: 2 of 192 were wrong without being flagged, both in blocks the model called high confidence. One was not a wrong reading at all, only a different notation, and the score still counts it:

The other was a lookalike:

I looked at the wrong ones instead of trying prompts. Of 199 wrong equations over three sets, 65% were ink, or a label, that a reader can’t settle from the page. Another 23% were a notation the label hadn’t used, 8% were misreads of clear ink, and 4% were writing the model left out. A model reading each expression alone from clean ink got 61% to 64% right, the same as reading the whole page. So the writing limits accuracy, whatever the prompt.

The model’s confidence told me almost nothing either: it separated right equations from wrong ones barely better than chance (area under the ROC curve, 0.52 to 0.61). So I stopped trying to raise accuracy and made the errors visible: on a page read from its image, every equation and every block with a formula in it goes to the instructor. I measured the cost by replaying the recorded answers. Required decisions per page went from 3.58 to 6.44 on scanned typed pages and from 2.00 to 5.69 on scanned papers. Silent wrong equations in those replays are 0 by construction.

Scans of typed pages worked better. Made into scans, 9 of the arXiv papers came out at 0.664 of equations exactly right, against 0.619 for the same papers as typed PDFs, at $0.136 a page. Since then I added pen-stroke checks for vector ink. A second reader and a choice of readings on the review card are built, and the second reader is off. The newest set did not test handwriting.

Tables: short of the floors I set

In the textbook run tables were off, so a detected table was kept as an image and sent to review. Since then tables are rebuilt as real tables. The layout model proposes ruled, shaded or header-marked grids only, so unruled tables and tables ruled only above and below were never proposed. On five real documents the detector found 14 of 25 tables (recall 0.560). Tracing each miss gave a list of mechanisms: the justified columns, a caption added after the decision, a page of sideways text, a page with more than 30,000 drawn items. The fixes took development recall to 0.920, which again says little.

On a fresh set of seven papers, registered before the run, it found 0.744 of the tables, and 0.914 of what it called a table was one. That missed both floors I had set, 0.85 for recall and 0.95 for precision. The misses there were Roman-numeral captions, bulleted cells and charts boxed by the layout model, none of which the development set had shown. I fixed the causes that run showed, so that set is now a development set. A local table set of 45 documents and 197 gold tables then gave a table-structure score (TEDS) of 0.941 with recall and precision of 0.985, and I don’t have a fresh test of these fixes.

Chemistry: the score, not the reading

The near-zero chemistry score looked like a failure to read chemistry, but it came mostly from how the score compares formulas. The sample was 443 chemistry equations in 12 development documents (79 pages), then 377 equations in five fresh OpenStax Chemistry sections, registered before the run.

What the score compared

The primary score compares the shape of the MathML. OpenStax writes a formula such as H2O(l) with a text run for each group of element symbols and the state symbol as three tokens. My converter, which also built the answer key for the authored document in the first example below, writes one upright letter for each symbol. What I counted

I put each of the 443 equations in one class, from the recorded answers, with no model call. In 244 of them the formula was right and the primary score was wrong only because of how the key spells it: how tokens are packed (75), how scripts are grouped (39), and upright against italic against text letters, bars, numbers and the length of an arrow (130). Counting those, 292 of 443 were right as chemistry. The primary score counted 48.

The fresh check

I didn’t change the registered score. I added a second one for chemistry only and report both. Then I wrote down predictions and ran the five fresh sections once, with no change afterwards. The primary was 0.135, which I had predicted would fall between 0.05 and 0.20. The chemistry score was 0.552 before the chemistry fixes and 0.560 after, 4.1 times the primary, against a prediction of at least 3.

After that I built what the reading needed: a species check on coefficients, charges, states and arrows, a subset of mhchem \ce notation, and MathML shaped so a speech engine pronounces it. MathCAT, a speech engine, recognized 153 of 153 correct chemistry outputs, up from 136. A second round of chemistry prompts did not clear its gate, so I didn’t ship it.

The newest set’s chemistry sections

The newest set included three OpenStax chemistry sections (123 equations), registered with a bar for chemistry. ReadableSTEM got 0.333 right as chemistry (41 of 123), against the 0.80 I registered. The control got the same 0.333, so the new checks added nothing here against my bar of 5 points. Silent harm was 18.70 per 100 (23 equations), against a bar of 1. None of those bars was met, and the registration calls this group not a success. With 123 equations in 3 sections, a rate near 0.33 has an interval of about plus or minus 0.08.

I report no chatbot comparison for chemistry. Both chatbots wrote their chemistry in mhchem notation, which my registered scorer does not convert, so their scores there say nothing about their chemistry.

What the tests leave out

  • The textbook sections are clean OpenStax pages from retired first editions, printed with my own stylesheet. Real course PDFs are harder.
  • OpenStax is public, so the models may have seen these books. I haven’t tested for that, and every Claude arm shares it.
  • I haven’t checked whether a wrong equation changes the meaning, or whether the figure judge agrees with a person.
  • Each arm ran once, so the newest set can’t show run-to-run variation, and a difference under about 3 points is not claimed either way.
  • The speech is ReadableSTEM’s own, not a particular screen reader’s. I have a written protocol for a VoiceOver test and no results, and none for NVDA or JAWS.
  • The arXiv answer keys follow the authors’ dollar-sign boundaries, and two of the three slide decks come from one repository, with relaxed gates.
  • The Opus chatbot’s cap was raised during the newest run, before I had seen any ReadableSTEM result, and the strong-prompt arm answered 17 of 29 documents.
  • The textbook results are for pipeline version 0.4.0, the version I registered, and the newest set is for 0.5.9. Every cause was found on my own development papers, and every fix was tuned on them. Only the fresh sets are evidence, and four of them are 15 papers.
  • The exact scorer is strict: hand-written LaTeX known to be correct scores 0.70 on a 40-equation sample, so exact numbers read low.
  • The handwriting is touchscreen ink from one dataset, pasted onto composed pages. It is not paper handwriting.
  • The table fixes, the LaTeX source path, the long figure descriptions and the Word and EPUB exports have no registered test.
  • In chemistry, the first edition and the Atoms First edition share text, so I chose topics the development set lacks and did not measure the overlap.
  • The chemistry score is mine, written after the problem was visible. To check it isn’t too generous, 15 pairs of near formulas must stay wrong in its tests, and on the authored document all 100 equations it calls right and the primary calls wrong have the same LaTeX once spacing, text commands and the arrow command are removed.

Lessons for your own evals

  1. Write down what “better” means before the run. The differences I care about most, heading levels and figures, are descriptive because I hadn’t registered them.
  2. Report a claim you didn’t make as not made. The claim I registered for the newest set needed silent errors under 4.0 and a flag recall of 0.60. I report it as not made, and the table floors and the chemistry sections the same way.
  3. Put every arm’s cost in the table, including the cheapest. The Haiku chatbot costs $0.0017 a page. A table with only the expensive arm would have hidden it.
  4. Count the errors nobody is asked about, not only the score.
  5. Split the misses by cause before you fix anything. One table of mechanisms, built from outputs I had already recorded and so free, showed that five causes carried most of the misses and that reading the math was not one of them. A score can measure markup rather than meaning, too: before you treat a low score as a failure, put a sample of the “wrong” answers in classes by hand.
  6. Ask what a repair loop could see before you build it. A render-and-compare check could see 1 of the 282 wrong equations nobody is asked about.
  7. When ink can’t be settled, stop tuning and show the errors. Raising accuracy had a ceiling. Sending every handwritten equation to a person did not.
  8. A zero in a small sample can fail to replicate, and numbers from the data you tuned on run high.
  9. Score what the user experiences, and test the scorer first. A screen-reader user hears speech, so the newest primary is spoken-equal, and I found and fixed a scorer bug the day before the run.
  10. Set spending caps from a measured cost per page. Mine came from a low estimate and stopped two chatbot arms early.
