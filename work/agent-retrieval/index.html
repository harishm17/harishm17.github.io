Finding the tables an agent misses

Following dbt lineage cut missed source tables from 79 to 24 on a 103-ticket benchmark.

Purgo AI, · 2026, · 5 min read

Updated October 14, 2026

My part. I built lineage expansion and its 48 tests, the schema check, the Pinecone search path and the catalog search benchmark, and I moved two stages to a smaller model, rewriting their prompts and setting reasoning effort per stage. The agent, its orchestration, the benchmark harness and the other prompts are the team’s.

Purgo’s agent is a LangGraph pipeline that turns a data-engineering ticket into PySpark, SQL and dbt code. Everything after retrieval depends on which tables reach the model’s context. If a table the ticket needs never arrives, the model either guesses a name, which later checks sometimes catch, or quietly leaves out a join, which nothing catches.

How I measured it

Purgo’s internal benchmarks are built from real tickets, and each ticket has a known answer that lists the tables it should use. A miss is one of those expected tables that never reached the agent’s context. I count misses across all tickets, so a ticket missing three tables counts three times. The benchmarks had between 95 and 103 tickets and ran at different times on different builds of the agent, so each result is compared with a baseline from its own run.

Following the lineage

When a dbt ticket names the model it wants changed, that model’s SQL already says which tables it reads from. So before any ranking, retrieval now parses the named model with sqlglot, follows its ref() and source() calls one hop, resolves sources through the names the project declares, and adds those tables to the candidates.

Note. Lineage expansion ran on 58 of the 103 tickets. On 18 of them it added at least one expected table, and on none did it lose one.

On the 103-ticket benchmark, missed source tables went from 79 to 24. Each added table costs about 154 tokens of context.

Adding a table to the candidates doesn’t mean it survives ranking, so I tested ways of handing lineage tables to the ranker. That was a separate run, and its baseline came out at 71 misses rather than 79, so read its rows against each other.

I also tried a simpler idea, searching the repo for files that look like the ticket and pulling in the tables they use. In another run, on 99 tickets, it ran on 87 and brought in 126 tables that no expected answer wanted, against 27 for lineage expansion in the same comparison. That’s a lot more noise for the ranker, so I dropped it.

Faster catalog search

For Iceberg catalogs on Polaris, I built a semantic search path on Pinecone that re-indexes only the tables whose schema changed. I compared it with Databricks Vector Search, the existing path, on 188 queries over a 282-table schema. The right tables for each query come from real tickets.

Against Databricks Vector Search, recall@10 (the share of expected tables in the top 10 results) was 0.68 instead of 0.54, and mean latency 0.18 s instead of 4.0 s per query. Precision@10 is only about 0.10, because search hands candidates to the ranker, whose job is to throw most of them away. This was one benchmark run.

Moving two stages to a smaller model

Retrieval and drafting ran on a larger model. I moved both stages to a smaller reasoning model, rewrote their prompts for it and set the reasoning effort for each stage, and switched only after comparing the two models over five runs of 102 tickets.

Retrieval recall was 0.931 with the larger model and 0.944 with the smaller one. The 0.013 difference is about the size of the 0.012 spread between runs, so I read it as no loss. Retrieval recall is the only quality measure I compared.

On the smaller model the two stages are 7.6 times cheaper, but they’re a small share of a full run’s cost. The code-generation stage carries most of it. Reasoning effort matters too: on one example ranking call, high effort used 3,712 reasoning tokens and took 31 s, while low effort used 210 and took 4 s.

Fewer wrong tables

Extra tables are the other failure, because each wrong one takes up context and can mislead the model. Some candidates named tables that don’t exist in the warehouse at all. Now, before the LLM ranks anything, a check compares each candidate with the warehouse’s actual schema and drops anything that isn’t there.

On 95 tickets, the share of wrong tables in context fell from 8.6% to 5.3%, and recall moved from 0.965 to 0.969. That’s one run with no confidence interval, and the change is small. The check does remove one kind of mistake entirely (tables that don’t exist) without giving up recall.

What this doesn’t show

  • I chose the lineage design on the same 103 tickets I report it on. There’s no held-out set, so the gain is probably a little optimistic.
  • The headline run and the lineage-variant run are separate runs. Both show about a 70% cut, so I trust the size of the effect more than any single count.
  • Lineage expansion follows one hop, so tables two models away still depend on search.
  • Everything here measures retrieval. I didn’t measure whether the generated code got more correct.
