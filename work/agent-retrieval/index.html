Purgo’s agent does a data team’s work from a ticket. The team describes a change it needs, such as a new report or a fix to a pipeline, and the agent writes the code: PySpark, SQL, or models in dbt (a tool where each table is defined by a SQL query, called a model).

A ticket rarely lists the tables that code needs. It names a report, a dbt model or a business term, and the warehouse holds hundreds of tables. If a needed table never reaches the LLM’s context, the LLM guesses a name or leaves out a join without saying so. Every extra table costs context and can mislead it.

So the design has two jobs: get the right tables into a bounded context, and catch code that would fail on a Databricks cluster or in dbt before anyone runs it. I built most of the retrieval, and several of the checks and the recovery logic in the review. The dbt lineage step is mine alone, from the idea to the ablation that chose its design. The diagrams mark each piece I built or reworked.

The agent is a multi-agent LangGraph system in a supervisor and worker layout. A ticket passes through five teams in order: research, requirement analysis, design, test data and code. The diagram above follows the same path and zooms in where I worked: its table-finding stages all sit inside research, and writing and reviewing the code is the code team.

Each team is a sub-graph whose supervisor hands work to its worker nodes, and supervisors route with a fixed table, not an LLM, which keeps a run repeatable and lets every worker be tested on its own.

Most of my work sits in research, which decides what the later teams see, and in the review at the end of the code team, which decides what ships. Research reads from a graph of the customer’s catalog: its tables, their columns and the lineage between them (which table is built from which). I built much of that graph retrieval with the team.

How it finds the tables

Retrieval is a funnel. It gathers every table that could matter from several sources, then narrows in steps that each remove one kind of mistake. Cheap, deterministic steps run first, and the LLM ranks only what survives them. Every step has a fallback, so one failing service never ends a run.

The candidates come from three sources because each misses something the others catch: the ticket’s own words, a search by meaning, and the inputs of a dbt model the ticket names. The union is deliberately generous, and the later steps narrow it.

Following the lineage

The trigger was one ticket that named only a report’s dbt model. The table it needed came 90th of 219 candidates, the ranker dropped it, and the agent joined the wrong table. Nothing in the ticket’s words pointed at the right table, but the dbt model’s own SQL did.

A dbt model’s SQL names every table it reads, through ref() and source() calls. Those inputs are its lineage. So when a ticket names a model, retrieval parses that model’s SQL with sqlglot (a SQL parser), follows the lineage graph one hop to the tables it reads, and adds them to the candidates. This takes no LLM call and adds at most 12 tables.

Semantic catalog search on Pinecone

For Iceberg tables in a Polaris catalog (an open table format and its catalog service), the agent had only keyword matching, and a first attempt at similarity search took about 14 s a query. I built a semantic search path on Pinecone, a vector database, behind the same interface as the Databricks path:

  • One index namespace per warehouse, catalog and schema, so a search covers exactly the schemas a project uses and two warehouses never mix.
  • Each table’s embedding weights its name 3 to 1 against its columns, matching how the Databricks path embeds, so results from the two paths rank alike.
  • Indexing is incremental: each table’s schema is hashed, so only changed tables are re-embedded.
  • If embedding fails it falls back to keywords, and an unreachable catalog is skipped.

On 188 queries from real tickets, recall@10 was 0.68 against 0.54 for Databricks Vector Search, and mean latency 0.18 s against 4.0 s.

Moving two stages to a smaller model

Retrieval and drafting ran on a larger model at high reasoning effort. I moved both to a smaller reasoning model, rewrote their prompts and set reasoning effort for each model tier separately, because the model that writes code rejects the lowest setting.

Over five runs of 102 tickets, recall was 0.931 on the larger model and 0.944 on the smaller, within the 0.012 spread between runs, and the two stages became 7.6 times cheaper. Effort also sets latency: one ranking call took 31 s at high effort and 4 s at low.

Checking the code it writes

Six checks run in parallel on every draft, and a failed review sends the errors back for a new draft, up to twice. I built several of the checks and the logic that decides what ships when every draft fails.

Lint rules for code that parses but fails on a cluster

Each rule comes from a real failure, such as pyspark.sql.functions helpers that don’t exist or syntax the cluster’s Python 3.11 rejects. The rules match on the syntax tree (AST) and stay quiet when unsure, because a false alarm sends a correct draft back.

dbt sources the repo declares

The LLM guessed source names differently on each run, and dbt failed to parse. Now the prompt lists the exact source() call for every declared table, and a check rejects any other.

Objections that don’t disappear

The LLM check’s objections used to vanish when it reworded them. Now each gets an identifier the next round must rule on, and contradictory requirements are reported once instead of driving drafts back and forth.

When every draft fails

The agent used to ship the latest, broken draft. Now it gets one more attempt with every draft’s errors and an instruction to change approach. If that fails too, it ships the draft with the fewest kinds of failed checks.

I also fixed the agent’s Langfuse traces (the record of each run), which dropped spans from worker threads and failed steps, so every run can be read back afterwards.

Smaller pieces of retrieval

Checking against the warehouse

Some candidates named tables that don’t exist: misspellings, guesses, or one table name tried under several catalogs when only one of them holds it. Before the LLM ranks anything, a check fetches each candidate’s schema and drops anything the warehouse doesn’t have.

It’s cheap because the agent needs those schemas anyway: they’re cached by full name and reused when the kept tables load. If the warehouse can’t be read, the check passes every candidate through. Wrong tables in context fell from 8.6% to 5.3% on 95 tickets, with recall about the same (0.965 to 0.969).

Searching the code repo

Existing code shows the model how a team writes SQL. GitHub’s code search returned fewer results for more keywords and hit rate limits at random, so I replaced it with a BM25 (keyword ranking) index per repo, cached by commit: a search takes under 1 ms and makes no API calls.

An LLM scores the top 20 files and keeps those at 65 or more, sharing a budget of 2,000 lines instead of a fixed snippet each. If the ranker fails, the BM25 files are kept; if it rejects every file, none are.

Fitting the context

Every source has a budget, so one large attachment can’t crowd out the tables: attachments get 60,000 characters ranked and 240,000 at most, lineage adds 12 tables per ticket, repo files share 2,000 lines with at least 80 per file, and the whole prompt stops at 100,000 tokens.

Truncated attachments raise no error: a requested table once arrived with 48 of its 117 columns, and a partial list reads like a complete one. So files are cut along their own structure: CSV at record boundaries, catalogs one table per chunk. Anything the ticket names is kept whole, and the rest is ranked by BM25 within its file. A closing note names every file that arrived incomplete.

The agent also sees a few sample rows per table. I sample them ahead of time from customers’ Databricks tables, and each project can turn on masking of personal data (Presidio).

What this doesn’t show

  • Everything here measures retrieval and the review’s design. I didn’t measure whether the generated code got more correct end to end.
  • I chose the lineage design on the same 103 tickets I report it on, so the gain is probably a little optimistic.
  • Lineage follows one hop, so tables two models away still depend on search.
