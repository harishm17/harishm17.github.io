Designing retrieval and code review for a data-engineering agent

How Purgo’s LangGraph agent finds the tables a ticket needs and checks the code it writes, and why each part is built the way it is. Following dbt lineage cut missed tables by about 70%.

A ticket rarely lists the tables it needs. It names a report, a dbt model or a business term, and the warehouse holds hundreds of tables. If a needed table never reaches the model’s context, the model guesses a name or quietly leaves out a join. Every extra table costs context and can mislead it.

So the design has two jobs: get exactly the right tables into a bounded context, and catch code that will fail on a Databricks cluster or in dbt before anyone runs it. I worked on both.

How the agent runs

The agent is a multi-agent LangGraph system in a supervisor and worker layout. A ticket moves through stages: research, requirement analysis, design, test data and code. Each stage is a team, a sub-graph whose supervisor hands work to its worker nodes. A run is picked by the ticket’s status, and each team writes its result back to the ticket, the repo or the workspace before the next one starts. The supervisors route with a fixed routing table, not an LLM, so a run is repeatable and every worker can be tested on its own.

Most of my work sits in the research stage, which decides what the later stages see, and in the review at the end of the code stage, which decides what ships.

How it finds the tables

Retrieval is a funnel. It gathers every table that could matter from several sources, then narrows in steps that each remove one kind of mistake. Cheap, deterministic steps run first, the LLM sees only what survives, and every step has a fallback, so one failing service never ends a run.

The candidates come from three sources because each misses something the others catch: the ticket’s own words, a search by meaning, and the inputs of a model the ticket names. The union is deliberately generous; precision is the next steps’ job.

The schema check comes before the ranker because it’s free and certain. The ranker comes last because it’s the one step that costs a model call and can be wrong in subtle ways.

Following the lineage

The trigger was one ticket that named only a report model. The table it needed came 90th of 219 candidates, the ranker dropped it, and the agent joined the wrong table. Nothing in the ticket’s words pointed at the right table, but the model’s own SQL did.

So when a dbt ticket names a model, retrieval parses it with sqlglot, follows its ref() and source() calls one hop, and adds those tables to the candidates, with no model call and at most 12 tables.

Each half covers the other’s failure: telling the ranker is enough on 93 of the 103 tickets, and putting tables back catches the 10 where it ignored the hint. In the headline run, a separate run on the same tickets, missed source tables went from 79 to 24, about 70% fewer, and no ticket lost a table it needed.

Checking against the warehouse

Some candidates named tables that don’t exist: misspellings, guesses, or a name expanded across catalogs that don’t own it. Before the LLM ranks anything, a check fetches each candidate’s schema and drops anything the warehouse doesn’t have.

It’s cheap because the agent needs those schemas anyway: they’re cached by full name and reused when the kept tables load. If the warehouse can’t be read, the check passes every candidate through. Wrong tables in context fell from 8.6% to 5.3% on 95 tickets, with recall unchanged.

Faster catalog search

For Iceberg catalogs on Polaris the agent had only keyword matching, and a first attempt at similarity in the service took about 14 s a query. I built a semantic search path on Pinecone behind the same interface as the Databricks path:

  • One index namespace per warehouse, catalog and schema, so a search covers exactly the schemas a project uses and two warehouses never mix.
  • Each table’s embedding weights its name 3 to 1 against its columns, matching how the Databricks path embeds, so results from the two paths rank alike.
  • Indexing is incremental: each table’s schema is hashed, so only changed tables are re-embedded.
  • If embedding fails it falls back to keywords, and an unreachable catalog is skipped.

On 188 queries from real tickets, recall@10 was 0.68 against 0.54 for Databricks Vector Search, and mean latency 0.18 s against 4.0 s.

Searching the code repo

Existing code shows the model how a team writes SQL. GitHub’s code search returned fewer results for more keywords and hit rate limits at random, so I replaced it with a BM25 index per repo, cached by commit: a search takes under 1 ms and makes no API calls.

An LLM scores the top 20 files and keeps those at 65 or more, sharing a budget of 2,000 lines instead of a fixed snippet each. If the ranker fails, the BM25 files are kept; if it rejects every file, none are.

Fitting the context

Every source has a budget, so one large attachment can’t crowd out the tables.

What reaches the research prompt, and its limit
SourceLimit
Attachments60,000 characters ranked, 240,000 at most
Lineage tables12 per ticket
Tables from the rankerScores of 70 and up, plus restored lineage tables
Repo files2,000 lines, at least 80 per file
The whole prompt100,000 tokens

Truncated attachments raise no error: a requested table once arrived with 48 of its 117 columns, and a partial list reads like a complete one. So files are cut along their own structure, CSV at record boundaries and catalogs one table per chunk, anything the ticket names is kept whole, and the rest is ranked by BM25 within its file. A closing note names every file that arrived incomplete.

The agent also sees a few sample rows per table, which I sample ahead of time from customers’ Databricks tables, with PII masking (Presidio) each project can turn on.

Moving two stages to a smaller model

Retrieval and drafting ran on a larger model at high reasoning effort. I moved both to a smaller reasoning model, rewrote their prompts and set effort per tier, not globally, since the code-writing tier’s model rejects the lowest setting.

Over five runs of 102 tickets, recall was 0.931 on the larger model and 0.944 on the smaller, within the 0.012 spread between runs, and the two stages became 7.6 times cheaper. Effort matters as much as size: one ranking call took 31 s at high effort and 4 s at low.

Checking the code it writes

Six checks run in parallel on every draft, and a failed review sends the errors back for a new draft, up to twice. I built several of the checks and the logic that decides what ships when every draft fails.

Lint rules for code that parses but fails on a cluster. Each rule comes from a real failure, such as pyspark.sql.functions helpers that don’t exist or syntax the cluster’s Python 3.11 rejects. They match on the syntax tree, not text, and stay quiet when unsure, because a false alarm sends a correct draft back.

dbt sources the repo declares. The model guessed source names differently on each run, and dbt failed to parse. Now the prompt lists the exact source() call for every declared table, and a check rejects any other.

Objections that don’t disappear. The LLM check’s objections used to vanish when it reworded them. Now each gets an identifier the next round must rule on, and contradictory requirements are reported once instead of driving drafts back and forth.

When every draft fails. The agent used to ship the latest, broken draft. Now it gets one more attempt with every draft’s errors and an instruction to change approach. If that fails too, it ships the draft with the fewest kinds of failed checks, never an empty one.

I also fixed the agent’s Langfuse traces, which dropped spans from worker threads and failed steps, so every run can be read back afterwards.

What this doesn’t show

  • Everything here measures retrieval and the review’s design. I didn’t measure whether the generated code got more correct end to end.
  • I chose the lineage design on the same 103 tickets I report it on, so the gain is probably a little optimistic.
  • Lineage follows one hop, so tables two models away still depend on search.
