Margins, a study app that makes you try before it helps

Margins plans a student’s days to the exam from their own course files. The student answers first, only unassisted answers count as mastery, and the server keeps the tutor from giving the answer away.

Margins is live at studymargins.com (opens in a new tab), free with a Google sign-in, and the code (opens in a new tab) is MIT-licensed on GitHub.

What it does

A student uploads lecture notes, book chapters and old exams. Margins proposes a course plan of units and topics, each tied to the pages that teach it, and the student edits it before anything is generated. They give an exam date and the minutes they have each day, and Margins lays out every day until the exam.

Each topic is a path of five steps. The AI writes the questions, grades the answers, finds the first wrong step and plans the days, and at every step the student has to answer before it helps. Everything is built from the student’s own files, so every question, explanation and answer points back to a page they can open.

What the tests show

Why the student tries first

Reading a clear summary feels like learning and mostly isn’t. In a 2025 PNAS experiment (opens in a new tab), students with a plain chatbot scored 48% higher on practice problems and 17% lower on a later exam taken without it. A tutor that held back the solution raised practice scores by 127% and left exam scores level with the control group. Both groups thought they had learned more than they had.

Margins keeps the effort with the student and uses the AI for the work around it, down to the smallest hint that unblocks. Code enforces the order, because a prompt alone can’t: in a study of an AI tutor (opens in a new tab) that beat in-class teaching, the platform had to sequence the help. Here the server holds the tutor’s hint level, every reply is checked for the answer before the student sees it, and the model has no say in whether an answer counts as unassisted.

How it works

Margins is two services on Railway and two stores.

Each service writes only its own tables. The AI service writes the knowledge graph (each topic’s concepts and how they depend on each other) and the generated question sets. The web service writes the evidence log, one event per answer, and the learner model computed from it, which is Margins’ record of what the student knows. That keeps a grading bug from corrupting the learner model, which can be rebuilt without calling a model.

From files to a knowledge graph

The AI service reads each upload as markdown, splits it into chunks that keep their heading path and pages, and embeds them in-process with bge-small-en-v1.5 into a pgvector HNSW index. No student text leaves the service to be embedded.

A topic is taught from at most 24 chunks, found by vector similarity plus Postgres full-text search and merged with reciprocal rank fusion. Generators see only those chunks, which keeps the prompt the same size as a course grows, and the shared excerpt block is prompt-cached across generators.

The first version scored every keyword match a flat 0.8, which made about half the results tie and come back in document order. Fusing ranks fixed that.

When a topic is first opened, an extraction job returns 3 to 8 concepts, each with two to five claims quoted from the source, and drops any quote that isn’t a verbatim substring of its chunk. Edges between concepts (needs, covers, easy to mix up with) carry a confidence, and cycles are broken. On 8 topics from two MIT OpenCourseWare courses, 149 of 149 claim quotes were found in their chunk, every topic had 3 to 8 concepts (5.9 on average) and an acyclic graph, and 155 of 155 generated items carried valid concept tags.

Generation runs when a topic is opened and never blocks the path: reading needs no AI and a student starts at once, and a warm-up that isn’t ready is skipped. Generating a whole course up front had spent $4.13 on 7 topics and used up the day’s budget. One topic’s six content types (concepts, warm-up, notes, worked examples, practice problems and a quiz) cost $0.928 in the latest run.

An event-sourced learner model

Every answer, from every screen, goes through one function that appends an evidence event: the concept, the score, the student’s confidence and an assistance level, which the screen sets and the model never does. Level 0 is a closed-book first try, 1 a failed first try, 2 an answer after being shown the material, and 3 an answer the AI carried. Only levels 0 and 1 update memory and mastery.

Memory is one FSRS card per concept. FSRS is an open spaced-repetition scheduler: it sets each review for just before the student would forget. The card’s state is a pure function of the event log, so a regrade, a rejected graph edge or a bug fix is “delete these events, insert those, replay”, where updating memory in place would need a migration for each.

Reviews count once per concept per local day, which stops a quiz, a practice set and a review on one afternoon from tripling a card’s stability. Writes for one student and concept take a Postgres advisory lock, in sorted order to avoid deadlock. Without it, under the default isolation level, two concurrent writers could each replay without the other’s event and the later commit would drop one.

Mastery is the recency-weighted mean of the last 5 unassisted scores, capped by how many separate sessions back it up (0.5 after one, 0.8 after two), times the card’s retrievability (FSRS’s estimate that the student can recall the concept now). A concept can’t be labeled solid without an unassisted success on a new question on a later day, so three right answers in one sitting don’t read as learned. A pass also credits the concepts it builds on, and a miss brings forward the review of the concepts that depend on it.

Trying first and then getting help never scores worse than asking for help first: each question has one first-try record, and later hints or a worked example only set flags. Any scale that gave credit for help would invite asking before trying.

Options I considered for what memory is attached to
OptionWhy not, or why
A card per question, as in AnkiQuestions are generated and varied, and a student rarely sees the same one twice. Per-question cards would repeat questions or never build a history.
One review schedule per topicToo coarse. One weak idea in a six-idea topic either drags the whole topic into review or hides in the average.
Elo, item response theory or knowledge tracingThese fit a difficulty to each question from many students’ answers. A course belongs to one student, so each generated question is answered by one person and its difficulty never gathers evidence.
One FSRS card per concept, replayed from an event logShipped. A concept is what a question probes. A fresh question is a harder test than a repeated card, which makes retrievability a little optimistic, and students see their unassisted accuracy, where that would show.

The study path and the plan

One pure function reads a topic’s state and returns the next activity with a reason, and the topic page, the plan and the Continue card all call it. It checks in a fixed order: repairs first (a concept that needs teaching after a failed try, then a wrong idea to fix), then warm-up, reading and recall, then a due review, and last practice or a quiz.

Teaching comes before re-testing: a failed first try is followed by pointers, the explainer or a worked example before the same idea is asked again. When a failed concept was simply due again at once, review re-asked it immediately and a struggling student looped.

The plan places new topics in prerequisite order, with a quiz the next day, spaced reviews, a mock exam after each unit and two full mocks before the date. The daily minutes are a hard cap, and a mock exam longer than that gets a day to itself. Review sessions mix up to 12 questions across topics (interleaving) and ask a fresh question after a miss.

A tutor that holds the answer back

The practice tutor works up a ladder of hints, from “what have you tried” to locating the problem, naming the idea and showing the general form. The server holds the rung (the current hint level): the model is told which rung it may use, and a pure function raises it by at most one per student action. Left to a prompt, a model asked “just tell me” five times slides up the ladder.

The tutor is handed the first wrong step as a fact: a deterministic function compares the numbers in the student’s working with the authored step answers and returns the first mismatch. Replies are capped at 80 words and one question.

Every reply is checked for a leak, meaning it gives away the answer. A string and number match runs first, then a Haiku judge looks for the answer in a rearranged form, the problem’s numbers plugged into a formula, or a worked example that reuses those numbers. A leaking reply is written again once, and if the rewrite leaks too, the authored hint for that rung is sent instead.

Ask is the chat where a student questions their course material. A small model sorts each message into lookup, logistics, understand, solve or check, and each intent has its own prompt. A lookup gets a direct, cited answer, an understand question first asks what the student thinks, and solve never solves the student’s own problem: its worked example uses different numbers and opens only after a real attempt. During a mock exam, an exam guard declines messages that match the exam’s questions, using word overlap and a small embedding model with no LLM call.

The threat model is accidental shortcuts. Answer keys stay on the server, except that practice is checked in the browser for instant feedback, where a determined student can read the key in the developer tools and cheat only themselves. The two failures that must never happen silently, a tutor leak and an assisted answer counted as unassisted, are enforced on the server.

Voice

In voice teach-back the student explains an idea aloud. The recall grader labels each claim, and its verdict picks the coach’s next move: a probe about the gap, a new example to apply the idea to, or a wrap-up. The coach explains only after two probes on the same gap, and the server enforces that order too.

A graded answer makes one model call instead of two in series: the server runs the grading step itself and hands the result to the coach as data. That cut the median time to the first spoken sentence from 2.8 seconds to about 1.1. The coach is Claude Haiku at low effort, at $0.0003 a turn in the test runs.

The browser streams the microphone to Deepgram Nova-3 with a short-lived token the server mints per session, which keeps API keys off the page. If the token or the stream fails, the browser’s own recognizer takes over in the same session and keeps the words heard so far.

Cost and reliability

Sign-up is open and spending is capped in code. Every model call goes through a budget check and a usage ledger, and the daily allowance ($8 for each student and $40 for everyone together, by default) is checked before a job is created.

Each purpose has its own model. Claude Opus writes notes, examples, quizzes and exams, because on my model-choice test only Opus cleared the correctness bar: Sonnet and Haiku made math errors. Sonnet at low effort writes the practice tutor’s replies and grades recall, and Haiku at low effort routes Ask messages, judges leaks and runs the voice coach.

The try-first core works without the AI, which has been down for days at a time, as in the credit outage of October 28.

Privacy

Deleting a course or the account deletes its files and everything made from them. Student material isn’t used for training by Margins or, by default, by Anthropic’s API, and a student’s margin notes and recall answers never go into prompts for anyone else. Voice audio goes to Deepgram, which is opted out of training and doesn’t keep it, and Margins stores only the transcript, for 180 days. I built AssemblyAI as a second recognizer and left it off, because it trains on audio unless a paid account opts out.

Other decisions

Smaller decisions, and what each gives up
DecisionWhy, and what it gives up
The learner model lives in the web service, in TypeScript, with one writerEvery interaction that produces evidence already ends in a web route, and FSRS then has one implementation. Database triggers would hide logic where tests and replay can’t reach it. Exam evidence lands when the student next loads the course.
FSRS-6 with default weights and 90% retention, not the newer FSRS-7The newer release was two days old, with a new async API and weights that can’t be converted. Fitting per-student weights needs about 1,000 reviews, which no student will have. A later move is a replay of the log.
No feature flag: a topic switches to the concept-based path when its concepts are extractedThere are few users and a merge deploys. A flag doubles the test matrix and leaves two products to maintain.
The reader shows extracted text, with no embedded PDF viewerExtracted text works for every file type and gives each chunk a stable anchor for margin notes and claims. Math and figures read better in the original, so every page links to it.
No OCRA scanned page has no text to cite. Scanned and handwritten files are not read yet.
Google sign-in onlyPasswords had no email verification and no recovery, and I removed them on October 28. Existing accounts kept their data by linking on a verified Google email. A student without a Google account can’t use Margins.

What the tests show

Scripted students play each conversation and code scores every reply, with no model as judge. The scripts include a confident wrong answer, three “I don’t know” in a row, “just tell me” and an instruction planted in the answer (a prompt injection). Each check has a bar it must reach to pass.

Ask passed on its third run of a 60-scenario set, whose first run leaked in 2 of the 71 replies about a student’s own problem, and again on the 132-scenario set in the table. In the passing practice run the leak check caught 18.0% of first drafts, and 2.9% of replies fell back to the authored hint. The tutor costs $0.0108 a reply.

The failing teach-back check counts sentences, and the turns it flagged were mostly greetings, acknowledgements and refusals that the count treats as lecturing. I have replaced it with a judge that reads each turn and haven’t yet run that on the full set.

In the generation run on 8 topics, a judge scored correctness 4.88, grounding in the source pages 4.91, teaching quality 4.78 and quiz question quality 4.50 out of 5, and listed 8 errors in 32 items, 2 of them mathematical. My own format checks on the notes failed: 0 of 8 had every expected section and 0 of 8 landed in the word band. The evaluation page (opens in a new tab) has the retrieval and generation detail, and every result file is in evals/results/ (opens in a new tab).

What isn’t measured

I haven’t measured whether students learn more with Margins. The tests show that the tutor withholds the answer and that retrieval finds the right pages, which the design needs and which is not evidence of learning. The leak checks are lexical, and a reply that teaches the answer in words the check doesn’t match would pass. Retrieval was tuned on the same 38 topics it is scored on, and the generation judge is the model that wrote the content, so I use both as regression guards. Voice hasn’t been tested on real devices for echo cancellation or iOS audio routing.
